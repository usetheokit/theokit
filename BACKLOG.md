# BACKLOG — theokit

The single registry of maintenance work for this repository. One place to answer *"what is
pending in theokit?"*

`theokit` is an **autonomous scope**: it is its own repository, with no umbrella above it, so the
registry lives at its own root. Ids are monotonic, never reused and never renumbered — a killed
`B-007` stays `B-007` forever, because the number is the audit trail.

The schema, the status transitions, the verdicts and the five intake gates are defined once, in
[`.claude/rules/cycle-backlog.md`](.claude/rules/cycle-backlog.md). This file is data; that file
is the contract. Do not restate one in the other.

## How an item gets here

Two producers, one schema:

| Producer | Arrives as | Evidence at intake |
|---|---|---|
| `/backlog-item {slug}` — a human noticed something | `status: raw`, `source: human` | `none-yet` — deliberately. A hunch is a legitimate thing to record and an illegitimate thing to plan against |
| `/discover --sweep {domain}` — a measured finding | `status: triaged`, `source: discover-{mode}` | a pointer, attached by the measurement |

A sweep finding skips intake because it arrives with the evidence intake is not allowed to
require. Everything else passes gates G1–G5 in `cycle-backlog.md § Hard gates`.

Nothing reaches a plan without passing `/discover`'s measurement: `raw → planned` is forbidden.

So the map has to be injected into each emitted entry at build time, per adapter, which makes this a change to the adapter contract rather than a change to the renderer.

  Recorded rather than attempted: this is an M3 parity criterion, and a half-wired version of it would be the shape this programme keeps finding.
