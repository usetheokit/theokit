# BACKLOG — theokit

The single registry of maintenance work for this repository. One place to answer *"what is
pending in theokit?"*

`theokit` is an **autonomous scope**: it is its own repository, with no umbrella above it, so the
registry lives at its own root. Ids are monotonic, never reused and never renumbered — a killed
`B-007` stays `B-007` forever, because the number is the audit trail.

The schema, the status transitions, the verdicts and the five intake gates are defined once, in
[`.claude/rules/cycle-backlog.md`](.claude/rules/cycle-backlog.md). This file is data; that file
is the contract. Do not restate one in the other.

## How an item gets here

Two producers, one schema:

| Producer | Arrives as | Evidence at intake |
|---|---|---|
| `/backlog-item {slug}` — a human noticed something | `status: raw`, `source: human` | `none-yet` — deliberately. A hunch is a legitimate thing to record and an illegitimate thing to plan against |
| `/discover --sweep {domain}` — a measured finding | `status: triaged`, `source: discover-{mode}` | a pointer, attached by the measurement |

A sweep finding skips intake because it arrives with the evidence intake is not allowed to
require. Everything else passes gates G1–G5 in `cycle-backlog.md § Hard gates`.

Nothing reaches a plan without passing `/discover`'s measurement: `raw → planned` is forbidden.

## B-005 — cache, observability, cost tracking and CSRF hardening ship with no production caller   [ ]

domain: theokit
repo: packages/theo
suggested_mode: review
source: discover-review
evidence: usetheokit/theokit#347 — `initCacheEngine` has zero production callers; the cache's `defaults` never reaches the engine; `createObservabilityPlugin` and the observability `resolveAdapter` appear only in tests; `trackAgentRun` has no production caller; `csrf-multi-header` is implemented and never exported; `action-encryption` is exercised only by its own test. Corrected 2026-08-20: the original wording said "`resolveAdapter` appears only in tests", which named two homonyms — the deploy registry's `resolveAdapter` (`packages/theo/src/adapters/registry.ts:41`) IS wired and dispatches `build --target` (`packages/theo/src/cli/commands/build.ts:222`); only the observability one is orphaned. It also said `trackAgentRun` "appears only in comments" when it has a unit test and a build assertion — the true claim is that it has no production caller
why_now: this is the Wave 0.5 pattern — subsystems built, tested and never connected. It is the cheapest work available (the code exists) and it gates the rest: with observability unwired, the agent-axis benchmark has no instrument
status: triaged
dod:
  - each named symbol either has a production caller exercised in a published build, or is deleted
  - the cache serves a hit on a second request, observed through its own signal rather than inferred
  - a run emits spans reaching an exporter from a production path, not from a test
  - CSRF hardening is reachable through a public export and on by default on the Web handler
  - this item is split into per-subsystem items at planning time if the wiring turns out to be more than one change
