# Migrating from TheoKit 0.2 to 0.3

0.3 turns on **strict CSRF** and an **enforced Content-Security-Policy** by
default. Most apps need only small, mechanical changes. This guide walks the
upgrade end to end and gives copy-paste recipes for finding the call sites that
need attention.

> **Install the pre-release while migrating:**
>
> ```bash
> npm install theokit@next
> ```
>
> The `@next` dist-tag tracks the 0.3 line so you can validate before the stable
> release lands.

## What changed in 0.3

### CSRF default flips from warn to strict

In 0.2, a mutating request without the `X-Theo-Action` header logged a warning.
In 0.3 it is **blocked with a 403** by default. Use `theoFetch` (which injects
the header) or add it manually. See §1 for the scan that finds affected calls.

### CSP default flips from report-only to enforce

In 0.2, Content-Security-Policy violations were reported to the console. In 0.3
the CSP is **enforced** (no `'unsafe-inline'`), so inline `<script>` and
`dangerouslySetInnerHTML` payloads are blocked. See §1 for the scan.

## 1. Scan for anticipated breakage

Before changing anything, let the framework tell you what will break:

```bash
theokit check --upgrade-readiness 0.3
```

The scanner is **lint-only** — it never edits your files. It reports three
classes of 0.3 violation with `file:line` and a suggested fix:

- `csrf-missing-header` — a raw `fetch(…, { method: 'POST' })` (or PUT/PATCH/
  DELETE) with no `X-Theo-Action` header. Under 0.3 strict CSRF these return
  `403`. Fix: use `theoFetch(path, { method, body })` (which injects the header)
  or add `headers: { 'X-Theo-Action': '1' }`.
- `inline-script` — an inline `<script>…</script>` (no `src=`) in an `.html`
  file. Blocked by the enforced CSP (no `'unsafe-inline'`). Fix: move it to a
  real script file loaded with `<script src="…">`, or thread `ctx.nonce`.
- `dangerously-set-inline-script` — a `dangerouslySetInnerHTML` payload that
  contains a `<script>`. Same CSP rule. Fix: load the script from a module, or
  thread `ctx.nonce`.

`--upgrade-readiness` exits `1` when it finds violations, so it doubles as a CI
gate. Pass `--allow-warnings` to keep the report but exit `0`.

## 2. Find the runtime call sites from a warn log

0.2 emits a `csrf-warn` structured-log event (one JSON line per blocked-in-0.3
request) so you can see the real traffic that will break, not just static
matches. Collect the warn log, then extract the affected paths.

### Variant A — with `jq`

```bash
jq -r 'select(.event == "csrf-warn") | .path' warn-log.jsonl | sort -u
```

### Variant B — Node-only (no `jq`; works on Windows / Alpine / minimal containers)

```bash
node -e "process.stdin.on('data',d=>d.toString().split('\n').filter(Boolean).forEach(l=>{try{console.log(JSON.parse(l).path)}catch{}}))" < warn-log.jsonl | sort -u
```

Count the total events:

```bash
node -e "let n=0;process.stdin.on('data',d=>n+=d.toString().split('\n').filter(Boolean).length);process.stdin.on('end',()=>console.log(n))" < warn-log.jsonl
```

Both recipes silently skip blank lines and malformed JSON, so raw log artifacts
are safe to pipe in. A sample log lives at
[`fixtures/0.2-to-0.3-warn-log.jsonl`](fixtures/0.2-to-0.3-warn-log.jsonl) and is
exercised by `tests/integration/migration-guide-recipes.test.ts` — if the
warn-event shape ever changes, that test fails and this guide is updated.

## 3. Apply the fixes

- Replace raw mutating `fetch` calls with `theoFetch`.
- Move inline scripts into real modules, or thread the request nonce.
- Re-run `theokit check --upgrade-readiness 0.3` until it reports zero
  violations.

## Rollback

If you need to revert temporarily:

```bash
npm install theokit@0.2
```

Pin `theokit@0.2` in `package.json`, reinstall, and your app returns to the
0.2 CSRF/CSP posture. Nothing in the 0.3 scanner mutates your source, so there
is nothing to undo beyond the version pin. Re-run the scanner before attempting
the upgrade again.

### Opt-out via config flag

If you want to stay on 0.3 but relax the new defaults while you finish
migrating, opt out per-concern in `theo.config.ts` instead of pinning the old
version:

```ts
import { defineConfig } from 'theokit'

export default defineConfig({
  security: {
    // 0.2 behaviour: log a warning instead of blocking the request.
    csrf: 'warn',
    // 0.2 behaviour: emit CSP violations to the console without enforcing.
    cspMode: 'report-only',
  },
})
```

`csrf: 'warn'` restores the 0.2 "warn, don't block" posture, and
`cspMode: 'report-only'` reports CSP violations without blocking inline
scripts. Treat both strictly as a **migration aid** — a temporary bridge while
you fix the `csrf-missing-header` / `inline-script` violations the scanner
reports — not a long-term setting. Flip them back to the strict 0.3 defaults
(`csrf: 'strict'`, `cspMode: 'enforce'`) as soon as the scan is clean.
