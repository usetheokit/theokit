## Target

`theokit@0.70.0`, installed from npm into a throwaway project — the published tarball, never the
working tree. `rules/acceptance-target.txt` declares `kind = library`, and `cycle-acceptance.md

That instruction is load-bearing and I learned it the expensive way. Three guesses at the authoring

.build()`; with that, the measurement became real.

### AC4 — passed, with the sibling that had to survive

No csrf option was passed anywhere: the criterion is about the DEFAULT, so supplying one would
grade a build nobody ships.

```
PASS  cross-origin POST, no token
      -> 403 | {"code":"FORBIDDEN","message":"CSRF check failed: Missing X-Theo-Action header"}
PASS  same-origin POST with the token header
      -> 200 | {"hi":"alice"}
PASS  GET, cross-origin
      -> 200 | {"ok":true}
```

The second and third cases are not decoration. A handler that rejected everything would pass the
first case while breaking the product, and a default that refused a cross-origin GET would be
over-blocking a request that changes no state.

### AC2 — the primitive holds; the path is unmeasured

`requireOwner(subject, ownerId)` answered 4/4 correctly against the published build, each with its
own reason: `subject does not own this resource`, `not authenticated`, and — the fail-safe that
matters most — `resource has no recorded owner` refuses rather than allows.

A correct primitive does not prove the path calls it. The published client surface is
`approve(approvalId, decision)` with no subject, so ownership can only be enforced server-side, and
ROADMAP names the gap in its own words: *the approval ledger records no owner, so two subjects
admitted to one agent can settle each other's approvals.*

### AC3 — the control was not armed, which is not the same as broken

`theoPlugin()` yields one plugin with `enforce` undefined, while ROADMAP describes the gate as a
`resolveId` hook at `enforce: 'pre'`. Calling `resolveId` directly, after `config()`, passed
`theokit/server/auth` through from a `.client.tsx` importer under `ssr: false`, `ssr: true` and
absent.

**That is a harness that failed to arm the control, not a demonstration that the control is
broken.** Not demonstrated is not disproved. Establishing AC3 needs a real `vite build` in a
scaffolded app, which is what the cycle prescribes and what this run did not do.

## Addendum — what this run produced after the verdict was computed

The verdict above stands: `NOT_VALIDATED`, computed from the evidence record, and M1's checkbox is
still `[ ]`. What follows is what the run went on to find, recorded here because an acceptance run's
value is not only its verdict.

### It found a blocker in the release it was validating

`theokit@0.70.0` — published about an hour before this run — answered **500 on every agent route** of
a freshly scaffolded, production-built app. Reproduced twice, the second time on an untouched
scaffold. `generateManifest` encodes agent paths against the project root it is told; `loadManifest`
guessed it as `dirname(serverDir)`, wrong by one level for the layout `create-theokit` scaffolds. So
the failing case was the default case.

Filed as usetheokit/theokit#871, registered as B-256, fixed, and published as **0.70.1**. Verified
after publishing on a scaffold created from the registry: `GET /api/agents/chat/approvals` answers
200 where it answered 500, and `POST /api/agents/chat` answers 403 from the CSRF gate — the route is
reached and its policy runs.

**This is the finding underneath the finding.** 8,269 unit tests were green while that shipped,
because none of them boots a scaffolded, built app. The acceptance phase exists for exactly the gap
those numbers cannot see.

### AC3's instrument now exists, and two more defects were measured with it

`scripts/probe-hydration.mjs` — an oracle B-229's Definition-of-done had named for a month and that
was in no commit. It drives Chrome over CDP with Node's built-in `WebSocket`; no browser driver is
declared anywhere in this monorepo.

It was proved to SEE before being trusted: pointed at a page that throws, it reports the exception
with its stack; pointed at a clean page, zero. That mattered — its first run against the scaffold
reported clean and proved nothing, because `ssr` is `default(false)` and the document arrived as
`<div id="root"></div>` at 531 bytes. With `.ssr(true)` the document is 15,324 bytes and the error is
immediate.

| found | where it went |
|---|---|
| React #418 on every SSR page — `ThemeSwitcher`'s `sr-only` theme announcement renders `light` on the server and `dark` on the client | `@theokit/ui`, a published dependency — usetheokit/theokit-ui#155 |
| scroll restoration persisted `0` instead of the offset the user left, because the save reads the DOM after React commits the incoming route | this repository — fixed in `ab8295dac`, proved by mutation and by a browser journey |

### What is still true about the verdict

AC1, AC2, AC5, AC6 and AC7 remain `not_exercised`. AC3's gate could not be armed outside a real
build and stays `not_exercised` — **not demonstrated is not disproved**. AC4 remains the one criterion
this run established, 3/3.

M1 does not close on this run, and the checkbox is correct as it stands.

## Addendum 2 — AC1's first half, established

`AC1` asks that the HITL approval path reject **an unauthenticated caller** and **an authenticated
non-owner**. Driven against `theokit@0.70.1` scaffolded from npm, SSR on, an agent whose policy reads
the subject, and the app's own `createContext`:

| identity | `GET /api/agents/chat/approvals` |
|---|---|
| none | **403 FORBIDDEN** — refused by the policy |
| `alice` | 200 |
| `mallory` | 200 |

**The first half holds.** The second does not have an instrument: both authenticated callers get an
empty list because nothing created an approval, and the published build exposes four aux routes —
`runs/:id/stream`, `threads/:id/message`, `threads/:id/stream`, `approvals` (GET) — and **no route
that settles one**. With no pending approval there is nothing for a non-owner to try to settle.

So AC1 is **partially exercised**, and the record says so rather than rounding it up.

### The first three measurements were my own fixture, and saying so is the point

The first run returned 403 for ALL THREE identities. Reporting that would have been a fabricated
defect against a framework that was correct. Three bisections, each killing one hypothesis:

1. **A `createContext` that throws** → `500 IDENTITY_UNAVAILABLE`, not 403. So it IS consulted. This
   also exercised B-254 — closed earlier today — in a real app: *the application could not resolve
   the caller* is now a different answer from *the application refused the caller*.
2. **A hardcoded subject, no header read** → **200**. So the wiring from `createContext` to the
   policy is correct.
3. **The header itself.** The node adapter hands `createContext` an `IncomingMessage`, whose headers
   are a plain object — not a Web `Request`. My fixture called `headers.get(...)` only. The
   framework's own smoke test reads both shapes; I had dropped the second branch.

`packages/theo/src/server/http/resolve-agent-subject.ts:19` documents this exactly — *"Headers and
cookies: yes. The request body: no."* — and reading it was what ended the hunt.

**Had I stopped at the first 403, this record would carry a defect that does not exist.**
