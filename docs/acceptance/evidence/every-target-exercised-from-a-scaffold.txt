What theo-cloud does NOT have, stated rather than implied
--------------------------------------------------------
A platform to upload to. The target builds and the artifact runs — measured above, and
its output is byte-for-byte the count the `node` target leaves (29 files each). There is
no TheoCloud service, and no command in this repository sends anything anywhere. That is
a product that does not exist yet, not a defect in the target, and the distinction
matters: a missing platform is closed by building one, while a broken target is closed by
a fix.

Four defects the deno-deploy path cost, each measured with a control
-------------------------------------------------------------------
1. A dot directory is never uploaded. `./.theokit/deno/probe.ts` failed the revision
   where the byte-identical `./visible/probe.ts` served HTTP 200.
2. No import map was emitted, and a prefix cannot stand in for one: Deno refuses
   `"theokit/": "npm:theokit/"` because the portion after the prefix is not URL-joinable
   onto an `npm:` URL. Exact per-specifier entries resolve.
3. `sloppy-imports` was absent; the default template carries six relative imports
   written with a `.js` extension against files on disk ending `.ts`.
4. The emitted instruction named `deployctl`, which talks to the previous Deno Deploy
   platform and answers 401 against a current token.

None was reachable by the 8747-test suite, and the build reported success in every case.
Two hypotheses were refuted along the way and are recorded because a refuted hypothesis
is what makes the surviving one worth something: the dot-directory theory was dismissed
once on a test whose upload still carried node_modules (so it failed for the other
reason), and the pnpm symlink theory was dismissed once against a cached upload that had
not changed at all.

The fifth cause, which is not ours and is left with a warning
-------------------------------------------------------------
Deploying the whole project root kept failing after the four fixes, and the cause turned
out to be Deno's own supply-chain policy rather than anything in the adapter. Measured by
reproducing the platform's condition locally — `deno check --node-modules-dir=none`:

    error: Could not find npm package '@theokit/agents' matching '^15.0.2'.
    A newer matching version was found, but it was not used because it was newer than the
    specified minimum dependency date of 2026-09-29 19:41:05 UTC.
    hint: This version is blocked by the minimum dependency age policy...

Deno refuses an npm version published inside a 24-hour window. The range comes from the
project's own `package.json`, which the upload carries — so a consumer who scaffolds right
after a TheoKit release cannot deploy to Deno until the window clears. It also explains
every earlier observation: the flat directory that DID serve carried no `package.json`, so
no range was applied and `npm:` resolved at latest.

Two separations that took measuring rather than reasoning:

  deno cache  --node-modules-dir=none   exit 0   module resolution is fine
  deno check  --node-modules-dir=none   exit 1   only TYPE checking fails (TS7034 on the
                                                 entry's lazily-initialised caches)

So resolution — the thing a deploy needs — works. What fails under `deno check` is type
inference on four cache variables in the emitted entry, and Deno Deploy does not type-check.

CORRECTED, same session: the paragraph above named the age policy as THE cause of the
platform failure, and a single-variable test refuted that as stated. Setting
`minimumDependencyAge: "0s"` in the generated `deno.json` did NOT make the deploy succeed.

What the deploy failure actually turns on, isolated by changing one thing at a time in one
directory:

    main.ts + deno.json + src/ + client/ + theo.config.ts      -> exit 0, /api/health 200,
                                                                  agent deltas "P" + "ONG"
    the same directory, plus package.json                      -> exit 1, revision failed

So the cause is `package.json` being in the upload. The age policy is the mechanism — Deno
reads the manifest, applies `^15.0.2`, and refuses a version inside its 24-hour window —
and the `deno.json` knob does not override it, because the manifest is what Deno resolves
against. Both halves are needed to state this correctly, and the first version of this
record had only one.

The adapter does NOT set `minimumDependencyAge`. Lowering it removes a supply-chain
protection, and that is the project owner's decision rather than a code generator's; a
default of 0 shipped by us would silently withdraw it from every consumer. What the
adapter now owes, and does, is that the failure be legible: the emitted entry names the
policy and the flag, because the error names the PACKAGE and nothing in it reads as
temporary.

Verified without the platform, which is what makes this claim checkable: the generated
entry and the generated config were run together under real Deno 2.9.5 from the scaffold
root — `/api/health` 200, `POST /api/agents/chat` 200 with deltas "P" + "ONG". The 8
specifiers the reader omits (test-only and client-side) are omitted correctly: the server
graph never needs them, measured rather than argued.
