# 0.3.0 Rollback Runbook

**Audience:** TheoKit release operator (single-maintainer scope today).
**Purpose:** copy-pasteable commands so a 0.3.0 regression response takes ≤ 5 min instead of 30+ min of improvisation.
**Read this BEFORE running T4.1 publish** (per the [`theokit-0-3-0-enforcement-cutover-plan`](../../../.claude/knowledge-base/plans/theokit-0-3-0-enforcement-cutover-plan.md) v1.1 dependency graph: T4.4 BLOCKS T4.1).

## When this runbook applies

A regression report arrives after `theokit@0.3.0` is on `latest` (T4.3 has executed). Symptoms:

- A user reports their 0.2-era app breaks on `pnpm install theokit@latest`.
- `/dogfood-stranger full` on a fresh `npx create-theokit@latest` returns a CRITICAL finding.
- Production traffic on a TheoCloud-hosted app surfaces unexpected 403s (CSRF strict path) or CSP violations.

If your symptom is NOT a CSRF/CSP-path regression, go to [§ When NOT to rollback](#when-not-to-rollback) instead — most "0.3.0 broke X" reports are unrelated to the strict-defaults flip and ship as `0.3.1` patches, not rollbacks.

## Decision tree

```
Regression report arrives
        │
        ▼
Is the failure in the CSRF or CSP enforcement path?
(check: does setting `csrf: 'warn'` + `cspMode: 'report-only'` make it go away?)
        │
   ┌────┴────┐
  YES        NO
   │          │
   ▼          ▼
ROLLBACK    SHIP 0.3.1 FIX
(this        (do NOT rollback;
 runbook)     keep 0.3.0 on `latest`)
```

## ROLLBACK procedure (CSRF/CSP-path regressions only)

### Step 1 — Verify the trigger

Before reverting the world, confirm the failure IS in the strict-defaults flip. Ask the reporter for:

1. The exact error / 403 message (must reference CSRF, CSP, Origin, Referer, Sec-Fetch-Site, or nonce).
2. Whether setting `csrf: 'warn'` + `cspMode: 'report-only'` in their `theo.config.ts` resolves the issue (per [migration guide § Rollback](../migration/0.2-to-0.3.md#rollback)).

If (2) is "yes, that fixes it" → rollback IS justified. If (2) is "no, still broken" → it's NOT a CSRF/CSP regression; SHIP a 0.3.1 instead.

### Step 2 — Roll back `latest` tag

```bash
# NEVER use npm unpublish — destroys the version forever (24h window only,
# and breaks anyone who depends on it). Use dist-tag to repoint `latest`.

# Repoint latest → 0.2.1 for both packages (linked invariant)
npm dist-tag add theokit@0.2.1 latest
npm dist-tag add create-theokit@0.2.1 latest

# (Optional) Tag 0.3.0 as 'rollback' so it's findable but not default
npm dist-tag add theokit@0.3.0 rollback
npm dist-tag add create-theokit@0.3.0 rollback
```

### Step 3 — Verify the rollback

```bash
# Both MUST return 0.2.1
npm view theokit@latest version
npm view create-theokit@latest version

# 0.3.0 should still be retrievable explicitly (NOT unpublished)
npm view theokit@0.3.0 version
```

If any verification fails → DO NOT proceed. Re-run Step 2. Open a GitHub issue immediately.

### Step 4 — Mark 0.3.0 as deprecated (advisory only — does NOT unpublish)

```bash
npm deprecate theokit@0.3.0 "Rolled back due to <regression-summary>. Use 0.2.1 OR follow workaround in https://github.com/usetheodev/theokit/issues/<NNN>"
npm deprecate create-theokit@0.3.0 "Rolled back. See theokit@0.3.0 deprecation message."
```

The deprecation warning surfaces in `pnpm install` / `npm install` output for anyone who explicitly pins `theokit@0.3.0`.

### Step 5 — Communicate

Post in this order:

1. **GitHub issue** — open a new issue titled "0.3.0 rolled back due to <regression-summary>". Reference the original regression report. Link to the deprecation message.
2. **Meta-repo `CLAUDE.md` Status table** — update `theokit` row to show `0.2.1 (latest; 0.3.0 rolled back, see issue #<NNN>)`.
3. **Migration guide** — add a banner at the top of [`docs/migration/0.2-to-0.3.md`](../migration/0.2-to-0.3.md) referencing the rollback.
4. **Blog post update** — if `docs/blog/0.3.0-release.md` is live, add a banner pointing to the rollback issue.

### Step 6 — Post-mortem

After the dust settles (within 48h):

1. Open a follow-up GitHub issue tagged `post-mortem` with the timeline.
2. Update the [`theokit-0-3-0-enforcement-cutover-plan`](../../../.claude/knowledge-base/plans/theokit-0-3-0-enforcement-cutover-plan.md) Accepted Risks section with the regression class.
3. Update `tests/e2e/` with a regression test that would have caught the failure pre-promote.
4. Plan 0.3.1 with the fix.

## When NOT to rollback

Do NOT execute this runbook if any of the following holds:

- The regression is unrelated to CSRF or CSP enforce path (e.g., a dev-server crash, a typo in a new error message, an unrelated dep update).
- The fix is small enough to ship as `0.3.1` within 24h.
- The regression only affects non-TheoCloud adapters (per cross-product invariant #5, those are opt-in compatibility surfaces without team validation; do NOT block the principal target on their breakage).

For these, the right action is:

1. Open a 0.3.1 hotfix branch from `develop`.
2. Add a regression test that fails on `0.3.0` and passes after the fix.
3. `pnpm version 0.3.1 --no-git-tag-version`
4. `pnpm publish --tag latest --access public` (no rollback; just patch forward).

## Why this is the convergent peer pattern

The 0.3.0 cutover blueprint Q5 + Q7 confirmed that 4/4 peer frameworks (Next.js, SvelteKit, Astro, Remix) document config-flag opt-outs as the canonical rollback path; no peer documents version-pin as the official rollback. The "downgrade via `npm install theokit@0.2 --save-exact`" path remains available (documented in [migration guide § Rollback § Full package downgrade](../migration/0.2-to-0.3.md#rollback)) but is the secondary recourse. The PRIMARY rollback for a CSRF/CSP regression is the config flag opt-out — which means in practice, this runbook fires only for the most severe case (config flag does NOT mitigate). Aligned with [ADR-0023](../adr/0023-csp-csrf-in-house-aligned-with-peers.md) (in-house implementation, owned end-to-end by the team).
