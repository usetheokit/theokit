# TheoKit 0.3.0 — security defaults that ship safely

Your app is now secure by default — and we ran 4 weeks of telemetry before flipping the switch, so we know it won't break yours.

## What changed in one line

CSRF goes from `warn` to `strict`. CSP goes from `report-only` to `enforce`. Per-request nonces thread through SSR automatically. One config line rolls everything back if you need a minute.

## The graduation pattern, compared to peers

We looked at how Next.js, SvelteKit, Astro, and Remix ship the same surface — and the answer surprised us. Here's the convergent map (every claim cited in [the cutover blueprint](../../.claude/knowledge-base/discoveries/blueprints/theokit-0-3-0-enforcement-cutover-blueprint.md)):

| Framework | Default posture | Rollback path |
|---|---|---|
| **Next.js** | Opt-in via example boilerplate (`with-strict-csp/middleware.js`) — never a framework default | Don't copy the example |
| **SvelteKit** | Opt-in via `kit.csp.directives` config — 9 `fix:` entries over 3 years, never graduated | Don't set the config |
| **Astro** | Graduated to default (`security.checkOrigin: true` since v3); `experimental.csp` → `security.csp` rename in v6 | Single config flag (`security.checkOrigin: false`) |
| **Remix** | `csrf-middleware` opt-in package; configurable strictness via `allowMissingOrigin` | Single config flag |
| **TheoKit 0.3.0** | **Graduated to default** (CSRF strict + CSP enforce) | Single config flag (`csrf: 'warn'`) + scanner-assisted detection |

TheoKit takes the harder path Astro takes — but with one differentiator nobody else ships.

## The differentiator: warn-mode telemetry

Before 0.3.0 became the default, we ran 4 to 6 weeks of warn-mode in 0.2.0. Your devtools `CsrfReadinessTab` counted exactly which requests would have failed under strict mode — same code path, no `403`, just a counter. When the counter hit zero across the dogfood-app runs for a full week, we flipped the default.

None of the 4 peer frameworks ship this. They flip the default and tell you to read the CHANGELOG. We flip the default after the data says it's safe.

## Rollback in one config line

If 0.3.0 breaks something we didn't catch, your `theo.config.ts` opt-out is one line:

```ts
import { defineConfig } from 'theokit/config'

export default defineConfig({
  security: {
    csrf: 'warn',          // 0.2.0 default
    cspMode: 'report-only' // 0.2.0 default
  }
})
```

This is a migration aid, not a long-term setting. Once your `CsrfReadinessTab` shows zero warns and your browser console shows zero CSP violations, remove the override. Full details in the [migration guide § Rollback](../migration/0.2-to-0.3.md#rollback).

If even the config-flag opt-out isn't enough, the [rollback runbook](../runbook/0.3.0-rollback.md) ships exact `npm dist-tag` commands so the rollback itself takes 5 minutes instead of 30.

## What to expect next

- **Scanner-assisted upgrades.** `theokit check --upgrade-readiness 0.3` scans your repo for the most common 0.2 → 0.3 incompatibilities and emits a checklist plus the migration-guide URL.
- **The 1.0 stability lock.** 0.3.0 is the last security-defaults flip before the 1.0 cutover. After 1.0, breaking changes require a migration codemod per [the roadmap](../../../CLAUDE.md).

## Architectural commitment locked

The decision to keep CSRF/CSP in-house (no `helmet`, no `csurf`) is documented in [ADR-0023](../adr/0023-csp-csrf-in-house-aligned-with-peers.md). The blueprint confirmed: zero of the 4 peer frameworks adopt a security-dep at runtime. The in-house path is the convergent industry pattern for this surface, not a one-off choice.
