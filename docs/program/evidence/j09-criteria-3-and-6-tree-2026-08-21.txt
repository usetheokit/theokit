VERDICT ON CRITERION 3 (tree, ungraded)
---------------------------------------
FAILS on the tree, and the two halves of the criterion cannot both hold with this
implementation:

  3.A is within tolerance of the human wait (+2.5%) and is 93.8% of the run span,
      so it is not "materially shorter than the run span".
  3.B and 3.C are comfortably shorter than the run span (31.5%, 28.2%) and are
      3.9x and 7.0x the human wait, so they are nowhere near tolerance.

hitl.resume_observed=true on all three, and the span status is ok — so the span
DOES close at the resume now, which is the improvement 0e9e6dc04 bought. What it
does not do is measure the interval the criterion names.

WHY, read from the wire rather than guessed. `closeToolSpan` keys on
`tool-output-available`, and the transcripts above show that chunk is not flushed
when the tool returns: in run 3.C the approval was answered at ~3306 ms
(3054 + 252) and `tool-output-available` reached the client at 4829 ms — 1523 ms
later, which is the model's post-resume latency. Filed as usetheokit/theokit#389;
this run reproduces it on a tree where the span closes correctly, which sharpens
the issue rather than restating it.

An application cannot fix this. The pause span is opened and closed inside
observe-agent-run.ts, an application supplies no chunk and no timestamp to it, and
`startSpan` takes a name, attributes and a trace context and nothing that would let
a caller end a span earlier. The journey file's older sentence about criterion 3 --
"an application cannot make it pass" -- is still accurate, for a reason that has
moved: the span used to never close, and now it closes on the wrong chunk.
