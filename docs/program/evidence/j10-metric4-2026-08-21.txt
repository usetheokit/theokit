TWO ASYMMETRIES, BOTH DECLARED, BOTH AGAINST THE READING BELOW BEING TAKEN AS J10's ANSWER:

1. What was timed is the LOCAL path - install, build, `theokit start` / `next start`, first HTTP
   answer - which is the same instrument every other journey in this sweep used and is therefore
   comparable across the sweep. It is NOT this journey's criteria. J10 grades a run on a target that
   is not the developer's machine, and both sides were graded in containers. Metric 4 on J10's own
   terms - wall clock to a green run on a deploy target - is NOT measured here and remains
   unmeasured. Recorded as a gap, not resolved by relabelling the local number.

2. The TheoKit lane resolves four of its dependencies from vendored tarballs in .vendor
   (theokit 0.49.0, @theokit/agents 10.1.0, @theokit/http 1.1.0, @theokit/presenter 0.7.0), built
   from the worktree because J10 needed an unreleased fix. Those are local file copies rather than
   registry fetches. With a warm cache a registry fetch is also served locally, so the difference is
   smaller than it sounds, but it is not zero and it favours the TheoKit lane.

Lockfiles, symmetric: both lanes carry their own tracked package-lock.json.
