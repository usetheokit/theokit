# i18n in this framework: nothing yet, and why that is an advantage

Measured 2026-08-20 against `packages/theo/src`, `packages/agents/src`, `packages/http/src` and
`packages/presenter/src`: no locale, message, catalogue or formatting module exists. The 2026-08-19
pass reached the same conclusion and it holds — this was re-checked rather than assumed. Two of the
supporting claims it made about *adjacent* machinery did not survive re-measurement, and both are
corrected below.

The sweep behind the headline claim:
`command grep -rniE "accept-language|locale|Intl\.|i18n|hreflang|dir=" packages/*/src` returns three
matches in the whole monorepo, and all three are comments explaining a decision to **avoid**
locale-dependent behaviour — `packages/theo/src/router/scan.ts:138`,
`packages/theo/src/server/scan/scan.ts:210` and
`packages/theo/src/server/_internal/compare-by-code-unit.ts:6`. The only locale awareness in this
codebase is the deliberate refusal to let `LANG` change a sort order.

## What exists

Nothing dedicated. What is present and relevant:

| Existing capability | Relevance | Evidence |
|---|---|---|
| The route table and its scanner | The input to locale-prefixed routing and per-route catalogue splitting | `packages/theo/src/router/scan.ts:128-171` |
| Route groups | The mechanism a locale segment can be built on without duplicating the tree — a `(dir)` contributes no URL segment | `packages/theo/src/router/scan.ts:112-113` |
| Middleware — but not on the document path | See the correction below | `packages/theo/src/server/http/middleware-runner.ts:71-80` |
| The typed client and route codegen | The machinery that can make message keys and locale-aware links type-checked | `packages/theo/src/router/generate.ts:136-150`, `packages/theo/src/cli/commands/generate-types.ts:1-45`, `packages/theo/src/client/link.tsx:54` |
| Metadata component | Where `dir` and alternates would land — though it has no prop for either today | `packages/theo/src/client/metadata.tsx:27-39` |
| A hardcoded `lang` in the served template | See the correction below | `packages/create-theokit/templates/default/index.html:2` |

**Correction to the 2026-08-19 measurement.** That pass listed *"Middleware — where negotiation and the
root redirect belong"* among existing capabilities. Middleware exists, but it does not run on the path
a document request takes. `runMiddlewareAndContext` is called from exactly two places: API route
execution (`packages/theo/src/server/http/execute.ts:141`) and action execution
(`packages/theo/src/server/http/action-execute.ts:169`). The production request handler enters the SSR
branch without ever calling it — the branch order is reserved routes, action, agent, API route, static
file, custom 404, then SSR (`packages/theo/src/cli/commands/start/request-handler.ts:250-262`). So
locale negotiation and a root redirect **cannot** be implemented in the existing middleware layer as it
stands: a request for `/` never reaches it. That is a wiring gap, not a design objection, but a plan
written from the earlier sentence would have assumed a hook that is not there.

**Correction to the 2026-08-19 measurement.** That pass did not mention `<html lang>` at all, which
left the impression that it is unset. It is set, and set wrong by construction: the scaffold's SSR
template hardcodes `<html lang="en">`
(`packages/create-theokit/templates/default/index.html:2`), as does the standalone demo shell
(`packages/create-theokit/templates/default/public/index.html:2`). The one place with no `lang` is the
static adapter's fallback document, used when no `index.html` is present
(`packages/theo/src/adapters/static.ts:146`). So every scaffolded project ships a document that
asserts English to screen readers and to translation tooling, regardless of who is reading it. For an
i18n plan this is worse than an absent attribute, because an absent attribute fails loudly in an audit
and a wrong one does not.

Note also that `lang` sits on `<html>`, which no React component can reach: the head rewrite injects
before `</head>` and never touches the opening tag
(`packages/theo/src/vite-plugin/hoist-head-tags.ts:101-118`). Whatever sets `lang` has to be the
template pipeline, not `<Metadata>`.

## Why the blank slate is worth something

Every mature framework's i18n story carries the shape of the decisions it made first, and most made the
same two badly:

1. **Locale handling was bolted onto a router that had no concept of it.** The result is a locale
   segment that behaves unlike every other segment, a link helper that must be remembered, and
   middleware that reimplements matching.
2. **Message handling was left to the ecosystem.** So the framework knows the routes and the library
   knows the messages, and nothing can split catalogues per route because no single component knows
   both.

Starting now means neither has to be true here. That is the whole opportunity, and it closes as soon as
the first design ships.

The one qualification the re-measurement adds: the blank slate is real for messages and locales, and it
is **not** a blank slate for the document shell, which already commits to `en`. That commitment was
made by a template rather than by a design, which is the easiest kind to undo — but it has to be undone
deliberately, not assumed away.

## Where this framework can be better

### 1. The locale is a route parameter the router understands

Not a middleware convention, not a userland segment: a first-class dimension of the route table, so
that a route is `(locale, path)` rather than a path with a prefix someone must remember.

Consequences that fall out for free:

* **Links carry the locale by construction.** The typed `Link` already knows the current route
  (`packages/theo/src/client/link.tsx:54`); making it locale-aware means a forgotten prefix is
  unrepresentable rather than merely discouraged. Every mature framework has a "you forgot to use the
  localised link" class of bug; this one need not.
* **Alternates are generated, not authored.** The framework knows the locale set and the route table,
  so the reciprocal set is mechanical — and the failure mode that silently produces nothing becomes
  impossible.
* **Static generation per locale** is a product of enumerating the locale dimension, not a separate
  feature. The static target already walks the route tree and writes one document per path
  (`packages/theo/src/adapters/static.ts:210-220`), so the locale dimension multiplies an existing
  loop rather than needing a new one.

### 2. Type-checked message keys, from the same generator that types routes

The framework already generates types from the route table
(`packages/theo/src/cli/commands/generate-types.ts:1-45`). Generating a union of message keys from the
default catalogue — with the placeholder shape per key — makes three defects compile errors:

```text
t('items.deleted')            ✓
t('items.delted')             ✗ unknown key
t('items.deleted')            ✗ missing required placeholder: count
```

No mainstream framework does this, because in every one of them the message layer is a separate library
that cannot see the build. Here it need not be separate.

### 3. Fail the build on catalogue divergence

Compare every locale's key set against the default's; fail on missing keys, unused keys and placeholder
mismatches. Runtime fallback then covers only the case that survives a green build, instead of covering
routine sloppiness.

Nothing like it runs today — `theokit check` is typecheck, eslint and the route scan
(`packages/theo/src/cli/commands/check.ts:7-9`). This is the item that changes how translation work
feels: a missing translation stops being a thing discovered by a user in production.

### 4. Per-route catalogue splitting

The framework knows which messages a route's components reference, and it already builds a per-route
preload map for exactly this kind of narrowing (`packages/theo/src/router/generate.ts:136-150`).
Shipping 4KB instead of 200KB is available to a framework and not to a library — and it is the single
largest byte win in this discipline for a large application.

### 5. Pseudo-locale as a built-in

A `--pseudo` locale generated from the default catalogue at build time, with no translator involved. It
finds every hard-coded string and every layout that cannot expand, in one pass, on day one. It costs a
transformation function and it is not standard anywhere.

## The order

Sequenced so each step is usable alone, and so the routing decision — the one that is expensive to
change later — is made first.

1. **Decide and document the locale model**: supported set, default, whether the default is prefixed,
   and the fallback chain. Written down before code, because every later step encodes it.
2. **Locale as a router dimension**, with locale-aware link generation. The foundational step;
   everything else assumes it.
3. **A hook on the document path.** Negotiation and the root redirect have nowhere to run today
   (`packages/theo/src/cli/commands/start/request-handler.ts:250-262`), so either the existing
   middleware layer grows a document-request stage or this surface gets its own. Decide which before
   writing the negotiation, because the answer determines whether the negotiated locale is reachable
   from a route handler at all.
4. **Negotiation itself**: proper tag matching with a declared chain, precedence order, and a single
   temporary redirect from naked paths only.
5. **`lang` and `dir` driven by the negotiated locale, replacing the hardcoded `en`**, plus reciprocal
   alternates generated from the locale set. Accessibility and discovery. Note this is a change to the
   template pipeline and to the scaffold, not to a component
   (`packages/create-theokit/templates/default/index.html:2`).
6. **A message module** with a standard message format — plurals and select from the start, never a
   ternary — plus rich interpolation.
7. **Type generation for message keys and placeholders**, from the default catalogue.
8. **Build gates**: catalogue divergence, placeholder mismatch, unused keys.
9. **Per-route catalogue splitting.**
10. **Pseudo-locale generation.**
11. **Formatting helpers** bound to the resolved locale — thin wrappers over the platform formatters,
    existing only so the locale does not have to be threaded by hand.

Steps 1–5 are the framework's unique contribution and should not be delegated to a library. Steps 6 and
11 could be a library; owning them is what makes steps 7–10 possible, and steps 7–10 are the ones that
would make this framework's i18n better than the incumbents rather than equal to them.
