  The 405 matters: it proves the route EXISTS and knows its own contract, which is a

THE PIPELINE WAS WALKED ONE REFUSAL AT A TIME. Each one was a different layer saying no,
and reading each instead of guessing is what got to the turn:

  1. POST with {messages:[{role,content}]}   -> 403 CSRF_FAILED: Missing X-Theo-Action
  2. + X-Theo-Action                          -> 400 "must contain a non-empty message
                                                      or messages[]"
     cause: parseAgentRequestBody accepts the ai-sdk shape {id, messages:[{parts:[...]}]}
     or the simple {message}. A {role,content} array matches the first branch's guard and
     has no `parts`, so the extracted text is empty.
  3. {message: "..."}                         -> 500 'Model "openrouter/openai/gpt-4o-mini"
                                                  declares provider "openrouter", but
                                                  OPENROUTER_API_KEY is not set.'
  4. LLM_MODEL=ollama/qwen2.5:1.5b            -> 200, the stream above

  Step 3 is CONFIGURATION, not a defect, and the error names the model, the provider, the
  variable and the two ways to fix it. No provider key exists in this session's environment:
  OPENROUTER, ANTHROPIC, OPENAI, GOOGLE, GROQ, MISTRAL, TOGETHER, DEEPINFRA, CEREBRAS, XAI
  all absent. Step 4 used a model already on this machine (4 pulled, nothing downloaded)
  through the keyless local path (`KEYLESS_API_KEY = 'local'`).

THE BROWSER UI IS WIRED. The built client bundle contains both `/api/agents/chat` and
`X-Theo-Action` — the header whose absence produced refusal 1 — so the UI sends what the
server requires.

================================================================================
DEPLOYED — the chat does NOT work on either target, for framework reasons

  cloudflare  /api/agents/chat -> 404
    The worker in the air predates B-312, which was silently dropping every agent. With
    agents included the upload now fails: @theokit/sdk resolves __dirname at module scope
    (B-314 / usetheokit/theokit-sdk#705), and Cloudflare executes the module at validation.

  vercel      /api/agents/chat -> 404   (was 500 before B-318)
    The function loads and runs — it answers its own JSON 404 — and finds nothing, because
    scanServerRoutes/scanAgents do a readdirSync against directories that are not in the
    lambda bundle. B-319. Cloudflare solved the same problem by baking the routes (#369);
    build-scan-routes.ts already produces that list and vercel.ts does not consume it.

  So the gap between "the chat works" and "the chat works where a user can reach it" is
  B-319 (vercel), B-314 + a redeploy (cloudflare), and B-317 for the document.
